# Instructions for an AI agent

You are editing a [Publii](https://getpublii.com/) site through `publii-agent`. Read this once, then work from the command catalogue.

## Installing

Ask the user before each install. Then:

```bash
python --version        # needs 3.10 or newer
pip install "publii-agent-toolkit[desktop] @ https://github.com/iMathieuB/publii-agent-toolkit/archive/refs/heads/main.zip"
publii-agent ops        # proves the install; lists every command
```

The `.zip` address needs no Git; a `git+https://` address fails on a machine without Git, which is the usual state of a fresh Windows. On Windows, check `python -c "import pywinauto"` before the first publish: on a machine without the Microsoft Visual C++ Redistributable it fails with "DLL load failed while importing win32ui", and `winget install Microsoft.VCRedist.2015+.x64` fixes it (ask first; Windows asks for elevation). A terminal that was open before winget installed Python does not see it on PATH: call `%LOCALAPPDATA%\Programs\Python\Python312\python.exe` by its full path.

If Python is missing or too old on Windows, propose `winget install Python.Python.3.12` and wait for a yes. If `publii-agent` is not found after the install (pip put it in a Scripts folder that is not on PATH), use `python -m publii_toolkit.cli` instead, with the same arguments. The `[desktop]` extra is Windows only and is what publishing needs; leave it out elsewhere.

Publii keeps each site in its own folder, by default `%USERPROFILE%\Documents\Publii\sites\<site>` on Windows and `~/Documents/Publii/sites/<site>` elsewhere. That folder, the one containing `input/`, is what `--site` takes. `publii-agent desktop-status` lists the sites it finds.

## The rules

**Ask the user how much you may do without asking.** If they told you to ask before every install, write or publish, show them the `plan` output in plain words and wait for a yes before each `apply`, and before each `desktop-sync --apply`.

**Close Publii first.** Every `apply` fails with `publii_running` while the app is open, and with `site_locked` if something else holds the database. That is a refusal, not a corruption, but you cannot proceed until the user closes the app.

**Read before you write.** Do not guess a slug or an id. Run `list_posts`, `get_post` or `get_site_settings` and use what comes back.

**Plan before you apply.** `plan` writes nothing and tells you whether every step can run. `apply` is all-or-nothing: one bad command in a batch means none of them land, so a plan that reports problems is a plan you must fix before applying.

**One batch per logical change.** Grouping related edits into a single `apply` keeps them atomic. A later command may refer by slug to a page an earlier command of the same batch creates, so a page, its menu entry and the setting that points at it belong together.

**Never edit the site's files directly.** Not `db.sqlite`, not the JSON under `input/config/`, not the media folder, not anything in `output/`. Every write must go through this tool, because that is what gives you the backup, the transaction and the integrity check. `output/` in particular is generated by Publii and any change you make there is discarded on the next sync.

**Never touch the deployment settings.** The server credentials (S3 keys, FTP passwords, tokens) are entered by the user in Publii. This tool cannot change them and never prints them; do not open `site.config.json` yourself to look.

**Report the backup path to the user** after a successful apply. It is in `result.backup`, and it is how they undo your work.

## The shape of every exchange

Send a JSON object. Get a JSON object back.

```json
{"ok": true, "result": {...}}
{"ok": false, "error": {"code": "...", "detail": "..."}}
```

Exit status is 0 when `ok` is true, 1 when it is false. Only JSON goes to stdout; logging goes to stderr.

## Commands

Get the current catalogue rather than trusting this list to stay complete:

```bash
publii-agent ops
```

Reads, available immediately: `list_posts`, `get_post`, `list_tags`, `list_menus`, `get_site_settings`, `check`.

Writes, through plan and apply: `create_page`, `update_post`, `update_meta`, `set_tags`, `create_menu`, `add_menu_item`, `remove_menu_item`, `update_menu_item`, `update_site_settings`, `set_s3_deployment`, `add_media`.

To rename a menu entry, use `update_menu_item`, not a remove and an add: the add puts the entry at the end of its level and reorders the menu.

### What to know about the new-site commands

**`create_page` and the editor.** Publii asks, page by page, which editor a page uses: `tinymce` (the WYSIWYG editor; the text is HTML such as `<p>Bienvenue</p>`) or `markdown` (the text is Markdown). The toolkit infers it only when every existing page and post uses the same one. A brand-new site has no page, so the first `create_page` must say `"editor"`. Ask the user: if they will edit the pages themselves later in Publii, `tinymce` is the one they will find familiar. `get_site_settings` shows which editors the site already uses. Slugs are lower-case words joined by hyphens (`a-propos`, not `À-propos`), unique on the site.

**`create_menu`.** A new site has no menu at all, so `add_menu_item` has nowhere to go until one exists. The positions you may use are the ones the theme declares, listed by `get_site_settings` under `theme_menu_positions` (the default theme has `mainMenu` and `footerMenu`).

**`add_menu_item` with `page`.** Pass the page's slug as `page` instead of an id as `link`, and the entry points at that page even if it is created earlier in the same batch.

**`add_media`.** Copies a local image (JPEG, PNG, WebP, GIF or SVG) into the site. With `"target": "logo"` it returns `media/website/<file>`, the value `update_site_settings` takes as `logo`. With `"target": "post"` and a page's `slug` it returns `#DOMAIN_NAME#<file>`, which you put in that page's text, for example `<img src="#DOMAIN_NAME#atelier.jpg" alt="L'atelier">`; add `"featured": true` and `"alt"` to make it the page's featured image. It never overwrites a different file of the same name: pass another `name`. Publii makes its smaller responsive copies of an image when someone uploads it in the app; images added here have none until the user regenerates thumbnails in Publii.

**`update_site_settings`.** Only these keys exist, everything else is refused: `site_name`, `site_description` (the default meta description), `logo`, `cookie_banner` (true or false: Publii's built-in GDPR cookie banner), `privacy_policy_page` (the slug of the page the banner links to), `front_page` (the slug of the page shown at the site root; without it the theme shows a list of blog posts there). The banner's own wording stays in Publii's settings.

**`set_s3_deployment`.** Fills Publii's "S3 compatible storage" server settings, all but the two keys: `website_url` (the site's address, e.g. `example.com`, written as `https://`), `endpoint` (the S3 endpoint without the bucket; for Cloudflare R2, `https://<account id>.r2.cloudflarestorage.com`), `bucket`, and `region` (default `auto`, R2's region). It writes the same values Publii writes when someone fills the form for R2 (read from sites saved in Publii 0.47.6 and 0.48.1), and leaves Prefix, ACL and the Cache-Control headers alone. The Access ID and the Secret key are refused: the user pastes them in Publii, Server, and clicks Save settings. Keys already filled are kept, and a site set to another server type (FTP, SFTP, GitHub Pages...) is refused. Afterwards, `get_site_settings` shows under `deployment` where the settings point and `keys_set`, which only says whether both keys are filled, so you can tell the user saved them without ever reading them.

## A worked example: a five-page site from a fresh Publii site

The user has created the site in Publii, typed the server credentials, and closed Publii. Everything below is yours, with their permission.

```bash
SITE="$HOME/Documents/Publii/sites/atelier-dupont"

# 1. What is there? A fresh site: no page, no menu, no editor in use yet.
publii-agent --site "$SITE" read '{"op":"get_site_settings"}'
publii-agent --site "$SITE" read '{"op":"list_posts","pages":true}'

# 2. Write the batch to a file, then plan it.
cat > site.json <<'JSON'
[
  {"op":"create_page","title":"Accueil","slug":"accueil","editor":"tinymce",
   "text":"<p>Réparation et entretien de vélos à Québec.</p>",
   "metaTitle":"Atelier Dupont, réparation de vélos à Québec",
   "metaDesc":"Réparation, mise au point et entretien de vélos, sur rendez-vous."},
  {"op":"create_page","title":"Services","slug":"services","editor":"tinymce",
   "text":"<h2>Mise au point</h2><p>Freins, vitesses, roues.</p>"},
  {"op":"create_page","title":"À propos","slug":"a-propos","editor":"tinymce",
   "text":"<p>Un atelier de quartier.</p>"},
  {"op":"create_page","title":"Contact","slug":"contact","editor":"tinymce",
   "text":"<p>Écrivez-nous ou passez à l'atelier.</p>"},
  {"op":"create_page","title":"Politique de confidentialité","slug":"politique-de-confidentialite",
   "editor":"tinymce","text":"<p>Les renseignements que nous recueillons…</p>"},

  {"op":"create_menu","position":"mainMenu","name":"Menu principal"},
  {"op":"add_menu_item","position":"mainMenu","label":"Accueil","page":"accueil"},
  {"op":"add_menu_item","position":"mainMenu","label":"Services","page":"services"},
  {"op":"add_menu_item","position":"mainMenu","label":"À propos","page":"a-propos"},
  {"op":"add_menu_item","position":"mainMenu","label":"Contact","page":"contact"},
  {"op":"create_menu","position":"footerMenu","name":"Pied de page"},
  {"op":"add_menu_item","position":"footerMenu","label":"Confidentialité",
   "page":"politique-de-confidentialite"},

  {"op":"add_media","file":"C:/Users/owner/Pictures/logo-atelier.png","target":"logo"},
  {"op":"update_site_settings","site_name":"Atelier Dupont",
   "site_description":"Réparation et entretien de vélos à Québec.",
   "logo":"media/website/logo-atelier.png","front_page":"accueil",
   "cookie_banner":true,"privacy_policy_page":"politique-de-confidentialite"}
]
JSON
publii-agent --site "$SITE" plan < site.json

# 3. Show the user what the plan says. On a yes:
publii-agent --site "$SITE" apply < site.json

# 4. Read back what you wrote, and give the user result.backup.
publii-agent --site "$SITE" read '{"op":"list_menus"}'
publii-agent --site "$SITE" check
```

The `logo` value in the last command is the one `add_media` returns: `media/website/` followed by the file name, with spaces turned into hyphens and accents removed. If the plan's description of the `add_media` step shows a different name, use that one.

Publishing is the user's call. The first render and the first sync happen in Publii, with the user watching, because that is where they confirm the server settings work. After that, and only with their yes:

```bash
publii-agent desktop-sync --name atelier-dupont          # dry run: says what would be published
publii-agent desktop-sync --name atelier-dupont --apply  # publishes, then confirms on disk
```

`desktop-sync` launches Publii itself, so Publii must be closed first, and it closes it again at the end.

## A smaller example: editing one page

```bash
publii-agent --site "$SITE" read '{"op":"get_post","slug":"about"}'
publii-agent --site "$SITE" plan '[
  {"op":"update_post","slug":"about","title":"About us"},
  {"op":"update_meta","slug":"about","metaDesc":"Who we are and what we build."}
]'
publii-agent --site "$SITE" apply '[
  {"op":"update_post","slug":"about","title":"About us"},
  {"op":"update_meta","slug":"about","metaDesc":"Who we are and what we build."}
]'
```

For anything long, pipe it on stdin instead of quoting it as an argument, as above with `site.json`.

## Errors you will meet

| Code | Meaning | What to do |
|---|---|---|
| `publii_running` | The Publii app is open | Ask the user to close it. Do not retry in a loop. |
| `site_locked` | Something holds the database | Ask the user to close Publii. Do not retry in a loop. |
| `plan_invalid` | At least one step cannot run | Read `result.steps[].problem`, fix every one, plan again. |
| `integrity_failed` | The result would have been structurally broken | The transaction rolled back and nothing changed. Report it; do not try to force it through. |
| `bad_command` | Malformed, or the target does not exist | Fix the command. |
| `bad_json` | The payload did not parse | Fix the JSON. |
| `io_error` | A file could not be read or written | Report the detail; check the path the user gave you. |

`integrity_failed` is the important one. It means the toolkit refused to leave the site in a state Publii could not open, for instance a menu pointing at a post that does not exist. Treat it as a bug in your plan, not as an obstacle to work around.

## What you cannot break

These hold regardless of what you send.

Writes take the database lock first and fail fast if Publii has it. The whole mutable surface, database and config, is copied to `input_backup/<timestamp>/` before anything changes. Database changes and config file swaps happen in one transaction, and the config swap is atomic. Images are copied under a temporary name and only moved into place just before the commit; a failed batch deletes them. A structural integrity check runs before the commit, and a failure rolls the entire batch back and restores the backup. Reads use a separate read-only connection. Settings outside the whitelist, credentials first among them, cannot be written.

What you can still do wrong is write bad content: a poor title, a wrong translation, a broken sentence, a page in Markdown where the user expected the WYSIWYG editor. Nothing here protects against that. Read what you wrote back before telling the user it is done.
