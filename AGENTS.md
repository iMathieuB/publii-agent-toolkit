# Instructions for an AI agent

You are editing a [Publii](https://getpublii.com/) site through `publii-agent`. Read this once, then work from the command catalogue.

## The rules

**Close Publii first.** Publii holds a write lock on the database. If it is open, every write fails with `site_locked`. That is a refusal, not a corruption, but you cannot proceed until the user closes the app.

**Read before you write.** Do not guess a slug or an id. Run `list_posts` or `get_post` and use what comes back.

**Plan before you apply.** `plan` writes nothing and tells you whether every step can run. `apply` is all-or-nothing: one bad command in a batch means none of them land, so a plan that reports problems is a plan you must fix before applying.

**One batch per logical change.** Grouping related edits into a single `apply` keeps them atomic. If updating a page and its menu entry belong together, send them together.

**Never edit the site's files directly.** Not `db.sqlite`, not the JSON under `input/config/`, not anything in `output/`. Every write must go through this tool, because that is what gives you the backup, the transaction and the integrity check. `output/` in particular is generated by Publii and any change you make there is discarded on the next sync.

**Report the backup path to the user** after a successful apply. It is how they undo your work.

## The shape of every exchange

Send a JSON object. Get a JSON object back.

```json
{"ok": true, "result": {...}}
{"ok": false, "error": {"code": "...", "detail": "..."}}
```

Exit status is 0 when `ok` is true, 1 when it is false. Only JSON goes to stdout; logging goes to stderr.

## Commands

Get the current catalogue rather than trusting this list to stay complete:

```bash
publii-agent ops
```

Reads, available immediately: `list_posts`, `get_post`, `list_tags`, `list_menus`, `check`.

Writes, through plan and apply: `update_post`, `update_meta`, `set_tags`, `add_menu_item`, `remove_menu_item`.

## A worked example

```bash
# 1. What is on the site?
publii-agent --site "$SITE" read '{"op":"list_posts","pages":true}'

# 2. What does this page look like now?
publii-agent --site "$SITE" read '{"op":"get_post","slug":"about"}'

# 3. Would this work?
publii-agent --site "$SITE" plan '[
  {"op":"update_post","slug":"about","title":"About us"},
  {"op":"update_meta","slug":"about","metaDesc":"Who we are and what we build."}
]'

# 4. Do it.
publii-agent --site "$SITE" apply '[
  {"op":"update_post","slug":"about","title":"About us"},
  {"op":"update_meta","slug":"about","metaDesc":"Who we are and what we build."}
]'
```

For anything long, pipe it on stdin instead of quoting it as an argument:

```bash
echo "$COMMANDS" | publii-agent --site "$SITE" apply
```

## Errors you will meet

| Code | Meaning | What to do |
|---|---|---|
| `site_locked` | Publii has the database open | Ask the user to close Publii. Do not retry in a loop. |
| `plan_invalid` | At least one step cannot run | Read `result.steps[].problem`, fix every one, plan again. |
| `integrity_failed` | The result would have been structurally broken | The transaction rolled back and nothing changed. Report it; do not try to force it through. |
| `bad_command` | Malformed, or the target does not exist | Fix the command. |
| `bad_json` | The payload did not parse | Fix the JSON. |

`integrity_failed` is the important one. It means the toolkit refused to leave the site in a state Publii could not open, for instance a menu pointing at a post that does not exist. Treat it as a bug in your plan, not as an obstacle to work around.

## What you cannot break

These hold regardless of what you send, which is why you can work without asking permission for every step.

Writes take the database lock first and fail fast if Publii has it. The whole mutable surface, database and config, is copied to `input_backup/<timestamp>/` before anything changes. Database changes and config file swaps happen in one transaction, and the config swap is atomic. A structural integrity check runs before the commit, and a failure rolls the entire batch back and restores the backup. Reads use a separate read-only connection.

What you can still do wrong is write bad content: a poor title, a wrong translation, a broken sentence. Nothing here protects against that. Read what you wrote back before telling the user it is done.
